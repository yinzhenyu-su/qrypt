# 任务复盘

任务完成、验收结束后，在最终回复前回看本次执行路径。优先使用当前对话中已经可见的操作、工具结果、时间和失败记录。日常收尾只做轻量检查，无合格建议时直接交付，显式要求复盘时可以简短说明结论。

## 筛选建议

- 找出具体摩擦及其证据，例如重复查状态、调用方反复拼装参数、可避免的重试或人工介入。区分必要的验收、权限确认和安全措施与可以消除的重复工作。
- 找到能解释摩擦的原因，优先提出覆盖原因的最小改动。可考虑调整流程、增强脚本或工具、改进 skill、重构接口。多个已知调用方需要同一个扩展点时，可以考虑预留钩子。跨模块反复出现的摩擦可以形成长期架构建议，先给出可独立验证的第一步。
- 依据复用机会、每次节省、实现和维护成本筛选。优先保留有重复迹象、明确复用场景或单次代价显著的改动。省略缺乏具体证据、缺乏可量化基线或仅把工作转移到别处的候选项。复盘给出建议，实施和有副作用的验证沿用原任务授权范围。

## 度量与验证

- **证据与基线**　说明从哪里看到问题，写出旧流程的计量边界、数值、单位和样本数。按问题选择指标，例如每个成功任务的工具调用数、实际操作数、人工介入次数、重试次数或端到端耗时。只使用可以从记录核实的数值，缺失指标留待采集。
- **改动与预期收益**　写明具体改动、复用场景和可检验的目标。用估计或目标标注预期值，并说明推算依据。包装原有调用时，同时看端到端成本与内部实际操作，避免只统计外层调用。
- **验证方法与实测收益**　用相同或等价的输入、权限和环境对照新旧流程，使用同一套验收标准，按需覆盖失败恢复等相关行为。确定通过条件，例如结果一致且每个任务的调用数至少减少一次。外部波动会影响结论时，用多次对照或后续同类任务复测。已验证时报告实测前后值、差值和样本数。证据不足时写「实测待验证」。

日常收尾只附上最值得做的建议，通常一条就够。让用户能看清观察、基线、改动、预期收益、验证方法及实测状态即可。
