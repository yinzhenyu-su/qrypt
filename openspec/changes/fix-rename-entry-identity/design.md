## Context

动机见 `proposal.md`。影响设计决策的现状：

- 身份冻结点唯一：`pkg/vfs/mutation/remote_rename.go:63-86` 只补 `Name`/`ParentID`，`pkg/vfs/view/commit.go:87-102` 原样写入视图；`view/resolve.go:93-95` 的缓存命中会直接返回该条目。
- 后端分成两类：标识由路径/键派生（`localfs`、`s3`、`webdav`、`sftp`、`baidunetdisk`、测试用 `fake`）与标识由后端分配且跨操作稳定（`quark`、`aliyundrive`、`onedrive`、`p115`、`p115open`、`p189`、`yun139`）。
- 视图侧有三层持有条目/标识：条目表（虚拟路径 → 条目）、目录列表缓存（TTL 10s，含子条目标识）、读缓存（以标识派生的 key）。`CommitRemoteRename` 只失效两个父目录的列表缓存，不迁移 `localDirs` 标记，且 shadow 的收敛令牌是操作前的标识。
- 既有可复用先例：`pkg/vfs/source_upload.go:110-121` 在 `driver.Rename` 之后用"列出父目录 + 按名字匹配"取回新条目；`Mkdir`/`PutSource`/`ServerSideCopier.Copy` 都返回条目。
- 约束：`pkg/crypt/drive_wrapper.go` 包装任意驱动并逐字转发标识，且当前连 `ServerSideCopier` 都未转发；`pkg/drivers/scopedfs` 与 `pkg/mobile` 的后端接口同样需要同步。
- 测试保真缺口：`pkg/drive/fake.go:431-432` 的 `Rename` 先 `rekey` 后改名，导致标识未变化；现有 VFS 级测试只校验远端文件系统，不做重命名后的本地读取。

## Goals / Non-Goals

**Goals:**

- 让"操作后的身份"由驱动提供，视图不得伪造，且该契约可被自动化断言验证。
- 重命名/移动之后，新路径的读取、写入前准备、列目录、删除都作用在后端的正确位置。
- 目录重命名后子孙身份不再陈旧；shadow 在名字到达目标后收敛并有兜底过期。
- 相邻一致性缺陷（覆盖目标的列表缓存、本地新建标记迁移）一并修掉。

**Non-Goals:**

- 不改变任何 provider 的远端 API 调用方式，不新增远端查询能力。
- 不改动重命名/移动对用户可见的语义、错误分类与任务模型。
- 不把路径解析能力接入运行时（对需要路径行走的后端过于昂贵）。
- 不引入持久化格式或配置项变化。

## Decisions

### D1: 扩展驱动签名，而不是新增可选能力

`Rename`/`Move` 返回 `(Entry, error)`，与 `Mkdir`/`PutSource`/`ServerSideCopier.Copy` 对齐。

- 备选：可选能力接口（仅路径派生驱动实现）。否决理由：包装驱动必须记得转发，而 `crypt` 未转发 `ServerSideCopier` 是现成反例；缺失即静默回落，缺陷只是变窄而非消除。
- 备选：VFS 侧反查（复用 `findSourceUploadedEntry` 模式）。不作为主路径：每次操作多一次远端列表，最终一致后端可能取不到，且路径派生驱动本可零成本算出新标识。
- 关键前提：新标识所需信息已在驱动内部算好（`s3` 的 `dstKey`、`localfs`/`sftp`/`webdav` 的目标路径、`fake` 的 rekey 结果），返回它不产生额外 I/O。

**两段式落地**，保证每个提交可独立通过 CI：

1. 纯签名重构：`drive.Driver`、`UnsupportedOperations`、全部 in-tree 驱动、包装驱动、适配层与测试假驱动改为返回条目，语义等价（返回传入条目），行为零变化。
2. 行为修复：路径派生驱动返回真实新条目；视图按返回身份提交；shadow/缓存/标记修复；契约断言与新回归。

### D2: 目录重命名的子孙身份采用"丢弃重取"

目录重命名时不再把操作前的子孙条目按新路径重键沿用，而是丢弃该子树条目，由下一次列目录回填真实身份。

- 备选：为路径派生驱动增加"由父标识 + 名称推导身份"的能力（零 I/O）。代价是需要 `crypt`/`scopedfs` 转发、需要按层级顺序推导，复杂度高于收益。
- 取舍：首次访问被丢弃的子项会多一次目录列表；远端收敛前可能短暂解析失败（与现状的"能解析但操作失败"相比，失败更早、更可诊断）。
- 若后续压测显示额外列表有痛感，再单独评估推导能力，不阻塞本次。

### D3: shadow 收敛判据以名字为准

收敛条件为"旧名字已从列表中消失且新名字已出现"，两端都按名字匹配，操作前记录的标识只作诊断信息：路径派生后端在重命名后上报的标识必然变化，继续按标识匹配会让 shadow 永不收敛。旧名字仍出现在列表中（远端尚未反映重命名）时保持隐藏，不暴露迁移未完成的陈旧项；当有不同对象被提交到旧路径时按标识立即 retire，使新对象立刻可见；最后由兜底过期（`RenameShadowTTL`）保证任何后端语义下旧路径都不会被永久隐藏。

- 备选：继续以标识匹配（现状）。否决：标识变化或最终一致会让 shadow 永不收敛，旧路径被永久隐藏，甚至让之后在旧路径新建的对象不可见。
- 备选：只按"新名字出现"收敛。否决：远端列表同时含新旧名字时（记录式列表的常见中间态）会立刻暴露旧名字，破坏 shadow 的原有作用。

### D4: 契约断言用"列表可验证"

契约测试在重命名/移动成功后列出目标父目录，断言其中存在标识等于返回条目的对象；对最终一致后端允许有限重试（次数与退避在实现时按既有等待模式确定）。

- 这是把"部分后端跨操作保持标识"这一当前无人验证的假设变成可执行检测；若某后端未来改变标识语义，断言会先红。

### D5: 不透明标识后端的契约条款与错误路径

- 契约文档明确：标识不透明的后端 MUST 保证其标识跨重命名/移动稳定；返回条目保留该标识并携带新的父标识与名称。
- 部分成功的错误路径保持不变：远端已改名但未迁移成功且回滚失败时，仍提交中间态条目。

### D6: 适配层同步范围

- `pkg/vfs/mutation`（`Remote` 接口、`RemoteRenamer`、backend 适配）与 `pkg/vfs/upload`（`RemoteOps`、`replace.go`、`target_index.go`）随之返回条目。
- `pkg/vfs/source_upload.go` 现有的"列出父目录 + 名字匹配"改为直接使用返回值；保留为异常兜底或删除，实现时按最小复杂度决定。
- `pkg/mobile` 的 scoped 后端接口同步签名。

## Risks / Trade-offs

- [签名扩散遗漏调用点] → 编译器强制 + 全量构建；契约矩阵与全驱动回归在第二步统一跑。
- [不透明后端"返回传入条目"等于未验证的假设] → 由 D4 断言把假设变检测；若某后端确实改变标识，改为在列表中反查（既有先例）而非放宽断言。
- [丢弃子孙条目后，远端未收敛时首次解析短暂失败] → 失败不写入负缓存；shadow 期间旧路径保持隐藏；必要时回退到 D2 的备选方案。
- [修 `fake` 的 `Rename` 会暴露既有测试红灯] → 逐条判定归属：断言了错误行为则修测试，暴露实现缺陷则修实现，不为变绿弱化断言。
- [覆盖已存在目标时新增一次列表失效 → 更多远端列表] → 仅覆盖场景触发；换来的是不再返回被覆盖目录的陈旧内容。
- [s3 幂等删除导致的静默失败属数据可见性问题] → 修复后删除按新标识执行，并以回归覆盖。

## Migration Plan

- 提交节奏：`refactor(drive): return the resulting entry from rename/move`（行为不变）+ `fix(vfs): commit the backend-reported rename identity`（视图与 shadow/缓存修复 + 测试）。两者可独立回滚，无数据迁移、无配置变化、无持久化格式变化。
- 回归范围：`pkg/contracttest` 契约矩阵、`pkg/vfs`（含 race）、`pkg/drive`、`pkg/crypt`、`pkg/mobile`、`pkg/drivers/*`。
- 回滚第二个提交即回到当前行为（缺陷复现），不产生不一致的本地状态。
