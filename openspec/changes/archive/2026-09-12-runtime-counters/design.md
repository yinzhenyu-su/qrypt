## Context

见 proposal.md - Why。设计相关的现状约束：

- `pkg/vfs/read/host.go` 已经确立了"诊断能力走可选 sink、不拓宽 Host 表面"的模式：`HealthRecorder`（`:32-37`）与 `ReadObserver`（`:44-56`）都是可选接口，各自带 no-op 实现，VFS 在装配时注入。计数器沿用这一模式，不新增 Host 方法。
- 读路径的记录点必须覆盖所有退出路径。`Reader.Read` 目前有三个提前返回（staging 打开失败、解析失败、远端读取失败）与一个成功返回，且开头已有一个 `defer` 记录健康结果（`reader.go:77`）。计数需要在每条路径上恰好记一次。
- bytes 的语义已有先例：读事件对 staging 直通路径记 `bytes=0`（`reader.go:98,103`），因为数据在 `Read` 返回后才由调用方消费；远端路径记 `len(data)`（内存中已物化）。计数器采用同一语义，避免出现"事件里是 0、计数里是别的值"这种两套口径。
- 无锁计数的先例在 `pkg/vfs/readcache/types.go:111-112`（atomic 的 hits/misses/puts/evicted），快照时读取为累计值。
- 快照装配在 `pkg/vfs/diagnostics`（DTO）+ `pkg/vfs/debug_runtime.go`（适配器）两层；`MountSnapshotRuntime` 是 per-mount 运行期数据的落点。

## Goals / Non-Goals

**Goals:**

- 提供与操作次数无关的定长累计计数：操作数、错误数、字节数、总耗时。
- 提供固定桶延迟直方图，使 p95/p99 在运行期可得，而不必保留单次耗时。
- 记录路径常数开销：无锁、无分配、无 per-op 存储。
- 通过 per-mount 快照暴露，消费方（`/v1/state`、`debug collect/watch/bundle`）零改动获得。

**Non-Goals:**

- 上传、删除、driver HTTP 的计数器（各自域内后续独立 change）。
- 健康阈值模型重构（绝对错误数 → 速率/分位）——本 change 只为其提供基数。
- 任何持久化、时间序列、跨进程聚合或 Prometheus/OTel 接入。
- 不替换或裁剪现有事件环形缓冲：事件回答"哪一次、慢在哪个阶段"，计数回答"总体多快、多稳"。

## Decisions

### 1. 无锁定长计数器 + 固定桶直方图，而不是"更聪明"的采样或衰减

替代方案与取舍：

- **按时间窗口重置的滑动统计**：与 `HealthTracker` 同构，但窗口本身会随吞吐自我截断，且"自启动以来的总量"无法回答。否决：累计量才是基线。
- **指数桶（HDR）直方图**：相对误差可控且桶数更少，但实现复杂度高、需要引入或自写一个结构。固定边界的桶在 1ms–5s 量程内已能满足 p95/p99 的判定，且边界是编译期常量、可被消费方直接读取解释。选择固定桶，代价是分位精度受桶宽限制（在文档与字段命名中如实说明为"桶上界"）。
- **保留最近 N 次耗时再排序**：需要 per-op 存储与锁，且 N 之外的分位不可得。否决。

### 2. 分位派生按"累计计数走桶"实现，结果报告桶上界

`Quantile(q)` 从最小桶向上累计计数，返回首次使累计 ≥ q×总数 的桶上界。理由：不做插值就无需假装精度；调用方得到的是"p95 落在 ≤100ms 桶"，对"是否长尾"这个问题的判断已足够。均值为 `总耗时/操作数`，与直方图独立但同源记录，测试断言两者一致。

### 3. 注入方式：新增可选 `CounterRecorder`，与 HealthRecorder 并列

```go
type CounterRecorder interface { RecordRead(bytes int64, elapsed time.Duration, err error) }
```
由 `pkg/drive.Counters` 实现，VFS 每挂载持有一个实例并在 `ReaderDeps` 注入。替代方案是把计数并入 `HealthRecorder`（少一个接口），但健康记录目前是 `RecordResult(op, err)` 的通用形状、被列表/上传等多处复用，塞入 bytes/duration 会让所有调用方为读路径的语义买单。保持独立接口，语义清晰且不扰动既有调用点。

### 4. 记录点：`Reader.Read` 的单一 defer，覆盖所有退出路径

在函数开头用一个 defer 记录：以命名局部变量累积 bytes（成功路径赋值），defer 里读取 `err` 与 `util.Now().Sub(started)`。这样"每个 Read 调用恰好记一次"是结构性保证，不会因为新增提前返回而漏记或重复。

bytes 的口径是**本次调用物化的字节数**：远端路径为 `len(data)`，staging 直通为 0（它只打开本地文件并把流交回调用方，数据在 `Read` 返回后才被消费）。这与读**事件**的 staging 路径不同——事件的 bytes 由 `debugReadCloser.finish` 在流关闭时用消费者实际读走的字节数记录（`reader.go:107-110`）。计数器有意选择"远端物化"口径：那才是消耗带宽与时间的部分，把它与本地直通的交付量混在一起会稀释吞吐的含义。差异在字段文档与 `docs/for-developer/debug.md` 中写明，不让读者以为两处必然相等。

## Risks / Trade-offs

- **[staging 直通路径的 bytes 为 0，吞吐看起来偏低]** → 与既有读事件口径一致（`reader.go:98,103`），不是新引入的失真；在计数器字段文档与 `docs/for-developer/debug.md` 中写明这一语义，避免被误读为"读得很慢"。
- **[固定桶精度有限，p99 可能被报告成桶上界]** → 有意为之：报告桶上界而非伪精度插值；桶边界随快照一起暴露，消费方可自行解释。
- **[直方图只覆盖 1ms–5s，超出者进溢出桶]** → 溢出桶参与分位派生，不会把长尾丢出总量；量程覆盖网盘读取的常见区间，且边界是常量、易调。
- **[累计量长时间运行后会溢出或失真]** → `uint64` 计数在可预见的运行时长内不会溢出；总耗时以纳秒累计，约 584 年才到 `uint64` 上限。
- **[与事件历史的数字可能不一致（同一时间窗内）]** → 两者口径不同（累计 vs 保留窗口）且 bytes 定义一致，文档写明"累计值不与保留窗口相等是正常的"。
